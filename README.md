# Machin Solutions

Marketing site for **Machin Solutions** — custom pergolas, tiki huts and outdoor living
structures in Miami and South Florida.

Live site: <https://machinsolutions.com> (once DNS is pointed — see
[Custom domain](#custom-domain))

---

## Stack, and why

| Layer | Choice | Why |
| --- | --- | --- |
| Framework | [Astro 5](https://astro.build) | Ships **zero client-side JavaScript by default** and renders every route to static HTML at build time. Nothing about the content, the metadata or the structured data depends on hydration, which is exactly what you want for a site whose job is to rank and convert. |
| Styling | Plain CSS with custom properties, scoped per component | No utility-framework payload, no build-time class scanning, and the whole design system lives in one readable file (`src/styles/global.css`). Astro scopes component styles automatically and inlines small stylesheets. |
| Images | `sharp`, run ahead of time via `npm run media` | Produces AVIF + WebP + JPEG at four widths from the originals. Running it as a separate step (rather than at build time) keeps CI fast and means the deploy does not depend on the original photo library being present. |
| Video | `ffmpeg`, same script | Re-encodes the source clips and extracts a poster frame for each. |
| Sitemap | `@astrojs/sitemap` | Generated from the routes that actually exist, so it cannot drift. |
| Hosting | GitHub Pages via GitHub Actions | Free, fast, static, and it serves a custom domain over HTTPS. |

**Why not React/Next:** a brochure site with a contact form has no need for a client-side
router or a hydration runtime, and both cost real Core Web Vitals budget. Astro gives
component reuse at build time without shipping a framework to the visitor.

**Why not a page builder:** the SEO architecture here — one primary keyword per URL,
hand-written structured data, explicit image dimensions — is easier to control and audit
in code than in a builder's UI.

## Getting started

```bash
npm install     # install dependencies
npm run dev     # local dev server at http://localhost:4321
npm run build   # production build into dist/
npm run preview # serve the built site locally
npm run audit   # post-build audit (see below) — run after npm run build
npm run media   # regenerate optimized images and video from the Gallery folder
npm run brand   # regenerate the favicon, app icons and Open Graph card
```

Requires **Node 20.3+ or 22+**. `npm run media` also needs **ffmpeg** on PATH for the
video steps (the script falls back to `D:\Installed programs\ffmpeg.exe`, and skips
videos entirely if it cannot find one).

## Changing the business details

**Everything goes in `src/config/site.ts`.** Phone number, email, address, licence
number, social profiles, opening hours and the contact-form endpoint are all defined
once and consumed everywhere — header, footer, every CTA, the contact page, and the
structured data.

Anything still written as `[SQUARE_BRACKETS]` is an unfilled placeholder. They are
designed to fail safely:

- A "Call" button with no real number links to `/contact/` instead of emitting a broken
  `tel:` link.
- Unverified fields (phone, address, licence) are **omitted from JSON-LD** rather than
  published as invented data.
- They render with a visible highlight so they are impossible to miss on the page.

Run `npm run build && npm run audit` at any time to get a full checklist of which
placeholders remain and which pages they appear on.

Content placeholders that live in copy rather than config are in `src/data/faqs.ts`
and in the page files themselves (`[PERMIT_POLICY]`, `[LEAD_TIME]`, `[WARRANTY_TERMS]`
and so on).

## Adding photos and videos

Originals live in `Gallery/` and are **never modified or committed**. The site is built
from optimized derivatives in `public/media/`.

1. Drop the new files into `Gallery/`.
2. Register them in `src/data/media.json`, under an existing project or a new one:

   ```jsonc
   {
     "id": "poolside-tiki-hut-kendall",
     "title": "Poolside Tiki Hut",
     "category": "tiki-huts",              // pergolas | tiki-huts | outdoor-living
     "summary": "One or two sentences about what was built.",
     "features": ["Sabal palm thatch", "Cypress frame"],
     "images": [
       {
         "src": "IMG-1234.jpg",                          // filename inside Gallery/
         "slug": "poolside-tiki-hut-kendall-01",         // becomes the web filename
         "alt": "Describe what is actually in the photo, naturally.",
         "hero": false                                    // true = candidate for a page hero
       }
     ],
     "videos": [
       { "src": "VID-5678.mp4", "slug": "poolside-tiki-hut-walkthrough", "title": "Short description" }
     ]
   }
   ```

3. `npm run media` — writes AVIF/WebP/JPEG at 480/960/1440/1920px (portraits cap at
   1440), extracts video posters, re-encodes the clips, and rewrites
   `public/media/manifest.json` with real pixel dimensions.
4. `npm run build && npm run audit`, then commit both `src/data/media.json` and the new
   files in `public/media/`.

**Alt text rules:** describe what is in the photograph in natural language. Do not stuff
keywords — the audit will not catch it, but Google will.

### Tiki hut photography

There is currently **no tiki hut or chickee hut photography in the gallery**. The
supplied Gallery folder contains 18 photos and 2 videos, and every one of them is a
pergola, cabana or outdoor kitchen.

Rather than caption a pergola as a tiki hut, the tiki hut pages use a drawn structure
(`src/components/TikiPlaceholder.astro`) and say plainly that photography is still to
come. When real tiki hut photos exist:

1. Add them to `Gallery/` and register them under a `"category": "tiki-huts"` project.
2. Run `npm run media`.
3. Replace `<TikiPlaceholder />` with `<Gallery projects={projectsIn('tiki-huts')} />`
   on `/tiki-huts/`, `/tiki-huts/chickee-huts/`, `/tiki-huts/construction/`,
   `/miami-tiki-huts/` and `/gallery/`.
4. In `src/components/ServiceCards.astro`'s call on the home page, replace
   `imageSlug: null` with the new slug.

## The contact form

GitHub Pages serves static files only — there is no backend, so **no endpoint has been
invented**. The form is fully built: labelled fields, client-side validation with
accessible error messaging, a honeypot, and a live status region.

To make it deliver mail, set one value in `src/config/site.ts`:

```ts
formEndpoint: 'https://formspree.io/f/xxxxxxxx',
```

Any service that accepts a `POST` of `FormData` and returns JSON works — Formspree,
Basin, Web3Forms, Getform, or a Cloudflare Worker of your own. Until it is set, the form
validates and then tells the visitor to call or email instead, rather than silently
swallowing the message.

## Deployment

Pushing to `main` triggers `.github/workflows/deploy.yml`, which runs `npm ci`,
`npm run build`, `npm run audit`, and publishes `dist/` to GitHub Pages. A failing audit
fails the deploy.

**One-time setup in the repository:** Settings → Pages → Build and deployment →
**Source: GitHub Actions**.

### Custom domain

`public/CNAME` contains `machinsolutions.com` and is copied into `dist/` on every build,
so the custom domain survives each deploy.

`astro.config.mjs` sets `base: '/'` deliberately. The site is served from the apex
domain, so all paths are root-relative. Setting `base: '/machin-solutions/'` would break
every link and asset once the domain resolves; `<user>.github.io/machin-solutions/`
redirects to the custom domain instead.

**DNS records to create at your registrar:**

| Type | Host | Value |
| --- | --- | --- |
| A | `@` | `185.199.108.153` |
| A | `@` | `185.199.109.153` |
| A | `@` | `185.199.110.153` |
| A | `@` | `185.199.111.153` |
| AAAA | `@` | `2606:50c0:8000::153` |
| AAAA | `@` | `2606:50c0:8001::153` |
| AAAA | `@` | `2606:50c0:8002::153` |
| AAAA | `@` | `2606:50c0:8003::153` |
| CNAME | `www` | `<github-username>.github.io.` |

Then Settings → Pages → Custom domain → `machinsolutions.com`, and tick **Enforce
HTTPS** once the certificate is issued (this can take up to 24 hours).

## The build audit

`npm run audit` reads `dist/` and fails the build on:

- broken internal links, and image/video/icon references with no file behind them
- missing or duplicate `<title>`, meta description or canonical
- pages with no `<h1>`, or more than one
- missing `og:image`, `twitter:card` or `lang`
- invalid JSON-LD
- `<img>` without `alt`, or without explicit `width`/`height` (the CLS guard)
- `localhost`, `example.com`, `127.0.0.1`, `lorem ipsum`, `TODO`, `FIXME`
- a missing `CNAME`, `robots.txt`, `404.html` or sitemap, or a sitemap URL with no page

It also prints a checklist of every intentional `[PLACEHOLDER]` and which pages carry it.
Warnings (long titles, meta descriptions outside 120–160 characters) are reported but do
not fail the build.

## SEO implemented

- **One primary keyword per URL.** The pergola hub targets the regional head term while
  `/miami-pergolas/` targets the city term, so they do not compete. `/faq/` deliberately
  answers questions that appear nowhere else on the site.
- Unique title, meta description, canonical and single `<h1>` on every page.
- Open Graph and Twitter Card metadata; the share card is generated from a real project
  photograph by `npm run brand`.
- Breadcrumbs on every inner page, with matching `BreadcrumbList` structured data.
- JSON-LD: `HomeAndConstructionBusiness`/`GeneralContractor`, `WebSite`, `WebPage`,
  `Service` with `OfferCatalog`, `FAQPage`, `ImageGallery`, `ImageObject`, `VideoObject`,
  `BreadcrumbList`. **No `AggregateRating` or `Review`** — there are no real reviews yet,
  and inventing them is both a policy violation and a lie.
- `robots.txt` and a generated `sitemap-index.xml` (the 404 page is excluded).
- Semantic HTML5, descriptive alt text, internal links with natural anchors.

## Performance

- Static HTML; the only client JavaScript is the nav toggle, the gallery lightbox, the
  sticky CTA and form validation — a few kilobytes, all deferred.
- AVIF → WebP → JPEG `<picture>` with `srcset`/`sizes` on every photograph.
- Explicit `width`/`height` on every image, enforced by the audit, so CLS stays at zero.
- The home page hero is preloaded with a responsive AVIF `srcset` and marked
  `fetchpriority="high"`; everything below the fold is lazy-loaded.
- Videos use `preload="none"` with a generated poster, so they cost nothing until played.
- One web font (Fraunces, one weight) with `preconnect` and `display=swap`; body text
  uses the system stack.

## Accessibility

Targeting WCAG 2.2 AA: skip link, semantic landmarks, one `<h1>` per page, visible focus
states, labelled form fields with `aria-invalid` and `aria-describedby` error messaging,
`aria-current` on the active nav item, `aria-pressed` on the gallery filters, a native
`<dialog>` lightbox with keyboard navigation and focus restoration, `alt` on every image,
and `prefers-reduced-motion` respected.
